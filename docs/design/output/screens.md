# Screens, and why they look the way they do

One paragraph per screen, keyed to `brief/03-screens-and-flows.md`. The artboard file in `canvas/` is named after each heading. Every screen is drawn at desktop 1280 (light), phone 390 (light) and phone 390 (dark); flows add a phone per step.

Example data is consistent across screens: the owner is m.hale@fastmail.com; Daniel and Sam are recipients; Priya, Tom and Lena are witnesses; the folder Estate carries a one-year rule.

## A. Public

**A1 Landing** (`Landing`). The page has to say what the thing is before it says anything clever, so the first line is the brief's own phrase, "A safe, not a drive", in the hero serif, with one sentence naming the kinds of things that belong in it. The five promises are a numbered ledger rather than a feature grid: numbered because they are commitments you can hold the product to, ruled like a document because that is the register the product speaks in. Promise five, "There is no recovery", is stated as plainly as the others, not tucked away, because the brief's tone asks that consequences are never softened. Two actions, create and sign in, nothing else to click above the fold. The hosted domain is a placeholder for the owner to fill.

**A2 Create account: the contract** (`Register`). Four full screens before any form, each with a step counter in mono, four ticks, the verbatim fact in the serif, the supporting sentences in the lead size, and one button. On phone the button sits at the bottom where the thumb is; on desktop it follows the text so the eye does not have to travel. The acknowledgement buttons say "I understand" rather than "Next", because the user is acknowledging, not navigating. The fourth screen is a single field; the button stays disabled (visibly, not hidden) until the phrase matches exactly, and a small "Matches" confirms it. Only then the form: three fields, the email field repeats "Cannot be changed later" in help text, and the strength line tells the person to write the password down somewhere that is not this safe, because there is nowhere else it can come from. "Check your email" shows the address in full so a typo is caught on the spot.

**A3 Verify email and A6 Not found** (`Verify`). Both are single short states with no navigation chrome; they should take one glance. Success is a check, one line, and Sign in. Failure says what happened in one line and offers the resend right there with the email field prefilled when the client knows it. Not found does not apologise and does not guess; it says nothing is kept at that address and offers the two places worth going. It deliberately uses the sans title: it is not a consequence.

**A4 Sign in** (`SignIn`). A narrow 400 px column with two fields and one button. Where other products put "Forgot password?", this one has a small lock icon and the verbatim "There is no password reset." in caption grey: present, honest, not shouted. Two-factor is a separate screen with one large mono code field (one field, not six boxes, so paste and autofill work) and a quiet switch to a backup code, which says each code works once.

**A5 Shared link** (`SharedLink`). The visitor has no account and may not know what CrypticStorage is, so the page is one card: the decrypted file name, size, a big Download, and the two limits the server enforces (expiry, downloads left) as plain lines. A small note says the file was decrypted in this browser, which is both true and reassuring. If there is a password it is asked first on its own screen. Expired, revoked and exhausted each get one specific sentence and the same one next step: ask the sender for a new link.

## B. Inside the vault

**B1 Locked** (`Locked`). Locking happens often, so this screen is designed as a resting state, not an error. The app chrome is gone (nothing decrypted can show), the serif says "Your safe is locked.", the account email sits under it so the person knows which safe this is, and the only field is the password. The small print states both lock triggers and that unlocking works offline. Sign out is a quiet action in the corner, not a competing button.

**B2 Dashboard** (`Dashboard`). This is the status page of the safe, so it opens with the one fact that matters most to an owner with rules: "Your sign-in today at 09:12 reset every handoff clock." Three tiles carry the counts the brief asks for (items, storage, rules) and nothing else. "For you" collects what needs the person's attention as someone else's witness or recipient, with the brief's sentences as the row titles. The rules list shows item, recipients, next date and state badge on every row, so nobody has to open a rule to know where it stands. Witnesses sit in the right column on desktop with their acceptance state, because a pending witness is something the owner should notice without looking for it.

**B3 Files** (`Files`). A list, not a grid: name first, then size and modified date as table columns on desktop and as a meta line on phone. Markers on each row say Shared with N or Link · N days left. When the folder itself has a rule, a tinted banner above the list states it in a sentence with the date, which keeps principle 4 (status where the item is) without decorating every row inside. Upload is a button and the whole page is a drop target, with a line saying files are encrypted before they leave the browser. Upload progress lives in a small tray on desktop and inline on phone, each line saying "Encrypting" while that is what is happening. Row actions are a ⋯ button that opens a menu on desktop and a bottom sheet on phone, with Delete last and in red.

**B4 Preview** (`Preview`). A large dialog on desktop and a near-full sheet on phone. Text is shown in mono on a plain card, images fit the width; the head has the name, the size, Download and Close. A one-line note says closing clears it from memory, which is what the person worried about leaving secrets on screen needs to hear. Anything that is not text or an image shows the same dialog with "No preview for this type" and Download.

**B5 Share** (`Share`). A segmented control picks With a person or With a link, person first because that is the first-class path. After the email, the dialog shows the person's fingerprint as eight mono groups and a Not verified badge, with one line saying how to check it and a switch to mark it checked. People already holding the item are listed with their verification state. The link tab asks for an optional password, an expiry as six chips, and a download limit as a stepper; once made, the URL sits in a read-only mono field with a copy button, and an amber callout says anyone with it can open the file. A key that changed since the last share raises the red callout from the component sheet, above the Share button.

**B6 Shared with me** (`SharedWithMe`). Two groups. "Set aside for you" lists owners who have named this person as a recipient, using the brief's sentence, so an inheritance is never a surprise. "Items" lists what can be opened now; released handoff items carry the hourglass and the verbatim "Handed off to you by {name}." on its own line, plus how and when it released. Everything else shows who shared it and when.

**B7 Settings** (`Settings`). Desktop is one long page with a fixed label column, because settings are rarely visited and scanning beats clicking through tabs. Email is read-only with the reason stated beside it. Password change notes that there is still no reset for the new one. The fingerprint is large enough to read aloud over a phone call. Witnesses is a summary and a link to its own page. "Lock and look" holds the auto-lock time and the theme override. Delete account is the last section with a secondary button in red text, never a red slab. On phone the page becomes an index list with the current value under each heading, and each section opens on its own.

**D Delete account** (`DeleteAccount`). The one-fact layout with the verbatim line, the supporting sentence, and a field asking for the account email. The fact stays in ink, not red: the colour is saved for the button, which reads "Destroy this safe" so the action names its result, and stays disabled until the email matches. The way out is "Keep my safe", which is kinder and clearer than Cancel.

## C. Handoff

**C1 Witnesses** (`Witnesses`). Its own page under Settings. The list shows each witness with acceptance state and the start of their fingerprint, the add field sits under it, and the threshold is a stepper reading "Release needs 2 of 4" with the bounds and the reason k is never 1 in help text. If a witness is also a recipient on any rule, the amber callout says so where it happens. Saving goes through one confirmation with the verbatim sentence and the full list of people under it, because "these" in "any 2 of these 4 people" needs the names in front of the reader.

**C2 Witness invitation** (`WitnessInvite`). Reached from email, so it opens without app chrome. The verbatim invitation is the serif line; the supporting sentence states the duty and the limit (you will never read those items). The two choices are Accept the duty and Decline, with "Decide later" in the corner, because a person should not feel rushed into a duty. After accepting, a calm sans confirmation says there is nothing to do now and where the request button will be.

**C3 Create a rule** (`CreateRule`). Started from a file or folder, so the sheet head names the item and its size. Recipients are added by email and each one shows that an account exists and the start of its key, catching a wrong address at once. Period is six chips. A plain callout restates the quorum path and when the reminders come, in the person's own numbers. Review leads to the one-fact confirmation with the verbatim sentence filled in with a real date, real addresses and the item name, which is the whole point: the person sees exactly what will happen and when.

**C4 Rules on an item** (`Rules`). From the item's sheet: state badge, recipients, period, next date, when the clock was last reset, and the witness threshold, as a short definition list, with Revoke as a quiet red action and "Add another rule" under it, since an item can go to different people under different rules. Revoking is one confirmation with the verbatim sentence and a red button that says Revoke rule; the way back says "Keep the rule". The dark phone shows the full rules list from the dashboard, with every state the owner can meet, including a rule that released by timer while they were away.

**C5 Recipient notice** (`RecipientNotice`). One screen, the hourglass, the verbatim sentence in the serif, the verbatim supporting line, and a single Done. A small line says the person can ignore it if they do not know the sender, which covers a mistyped address without alarm. The same sentence appears as a row in Dashboard › For you and in Shared with me.

**C6 Request a release** (`Release`). On the witness's dashboard, each owner they serve is a card listing the witness set and, if a request is open, who voted, a vote bar in amber and the reminder that the owner signing in cancels it. Opening a request and adding a vote are both one-fact screens with the verbatim sentences. Opening uses the primary button because it can still be undone by the owner; the vote that may complete a release uses the danger button, because that sentence ends "This cannot be undone."

**C7 Release notice** (`ReleaseNotice`). For the owner, the dashboard's top card tells the story as a short timeline: who opened the request, who voted, and how it ended, each a line with who and when. The common case on return is "Your sign-in cancelled a release request", and it is designed to reassure: the witnesses have been told and nothing was released. The released case states where the item went and that the owner's own copy is unchanged.

## E. Admin

**E Admin** (`Admin`). A fifth nav item visible only to admins. The subtitle states the boundary before anything else: accounts and storage, never items, names or keys. Creating an account is one email field, with help text saying the person sets their own password. The table has exactly the brief's columns, quota as words plus a bar so it scans, and Set quota on each row. On phone the table becomes a list.

## F. Emails

**F Emails** (`Emails`). Plain text, a subject, two sentences, one link, as the brief asks. The design rule that falls out of the zero-knowledge promise: no email ever names an item, because the server cannot read names. Copy says "what the rule covers" instead. The full text is in `emails.md`.
